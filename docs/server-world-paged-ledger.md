# Bounded contribution spill and paged publication

This is a follow-up storage adapter, independent of the retained core mode and 005 whole-array outcome API. It is not enabled by startup configuration in this checkpoint. Actual Area/host mode integration, simultaneous source-RNG reservation, production recovery scheduling and load validation remain the respective core/host owners' work.

`server/world/contribution-store.ts` exports `DurableOutcomeStore`. Its constructor requires the actual pure core `planOutcomePage` and a versioned `CoreCharacterCodec`. SQL never derives quest eligibility or reward formulas. All character IDs are canonical lower-case UUIDv4; native UUID ordering and text `COLLATE "C"` match JavaScript canonical UUID lexical order.

## IO and lifetime bounds

`recordContributionBatch` accepts 1..100 core `CreditWrite` values. Each credit is at most 4096 UTF-8 bytes. Writes coalesce by victim/character to the latest version, equal versions must have identical canonical content, older observations do not overwrite newer ones. Victim advisory transaction locks and sorted character FK locks serialize independent processes. A batch either commits every accepted write or none. There is no lifetime contributor-count eligibility cap. The database keeps one latest row per contributor to a live victim; JavaScript only handles a bounded batch/page.

The source tracks two distinct counters. `throughVersion` is the largest accepted victim-specific observation version. `sourceVersion` is a durable mutation revision: a later new contributor with a lower observation version still changes it. Summary fences cannot rely on the largest version alone.

`readContributionSummary(victim,residentIds<=100)` locks one victim and returns source counters, total contributors, stored `cogEligible` count, and sorted requested residents with their prior credit plus eligible prefix count. A new source has zero counters and null prior credits. SQL counts only the core-supplied boolean. It does not independently decide eligibility. This summary supports a bounded pre-step core RNG reservation. The host must flush ALL dirty credits for the victim and obtain the final source summary before freezing; an old pre-step summary is not a final durable fence.

Each query has an explicit operational timeout (default 5000ms, configurable) and every transaction sets a database `statement_timeout`. Failure is retryable backpressure; source obligations are not ACKed or dropped. A timed-out or disconnected COMMIT may be ambiguous, so callers read back immutable draft/page/seal authority before retrying source retirement. Timeout is not a reward eligibility policy or a permanent healthy-database contributor budget.

## Freeze, pages and publication

1. Capture a pure core `DeathRecipe`, with bounded resident overrides and reserved RNG state. Freeze only after dirty writes are durably drained. Call `beginVictimDraft({recipe,fence:finalSummary})`. Both source counters and the recipe through-version must match the durable source exactly. The actual pure core verifyDeathRecipeSummary also checks expected contributors and expected RNG draws using the final summary and resident overrides inside the same transaction. A committed draft changes its source to `frozen`, rejecting later observation changes. Recipe and initial cursor retries must be identical. Existing unsealed 005/legacy grant prefixes cannot be converted into a paged outcome.
2. `readContributionPage(draftId,afterCharacter,limit 1..100)` reads frozen credits in stable canonical character order. Only the core planner computes grants. `appendVictimPage` recomputes the submitted page using that planner and the actual frozen credits/cursor. It rejects gaps, altered contents, changed cursors and recipients. A single transaction inserts visibility intent first, then the immutable physical grants, page proof and next cursor. The visibility-to-grant FK is deferred until commit, so dangling intent cannot survive a failed page. Retry of the same page is idempotent across processes. A failed page rolls back all rows and cursor changes.
3. The migration renames the physical journal to `world_character_grants_physical` and preserves the original `world_character_grants` name as a filtered automatically updatable view. Both the original name and `world_replayable_grants` hide staged rows until the complete paged seal exists. Character pending/recovery/receipt-save paths all read this view; a staged ID cannot be receipted early. No page is independently published.
4. `sealVictimDraft` requires the complete frozen recipient set, exact expected recipient/draw counts, and stores one constant-size immutable seal. Publication is a view join to that seal, so this operation neither constructs an N-element JavaScript array nor copies N grant rows in one transaction. Empty outcomes seal their initial cursor without an empty page. `getVictimSeal(victim)` returns either the original 005 `whole-v1` seal or the new `paged-v1` seal, preserving 005 semantics.

`paged-v1` uses a separate `sha256-chain-v1` digest scheme. The initial chain binds victim, codec, recipe digest, frozen count and through-version; each canonical grant row advances it. The chain is independent of page partition. Page proofs separately bind cursor/progress. Do not compare this digest with 005 `sha256-flat-v1` or reinterpret old 005 manifests. The final cursor preserves exact RNG continuation and recipient/draw counts. Host source retirement requires the complete seal and matching recipe/digest, never just an append response.

`getVictimDraft(draftId)` returns the durable recipe, cursor, chain and counters for restart without a live Area. A sealed draft uses `getVictimSeal`; bounded cleanup may already have removed its temporary metadata. No raw cookie, provider credential or client checkpoint belongs in these APIs.

## Recurring recovery and ownership

Drafts receive a unique indexed bigint `recovery_sequence`. Keep it as a decimal string. Capture `getDraftRecoveryHighWater()`, then call `listVictimDrafts({afterSequence:'0',throughSequence:highWater,limit<=100})`. Process at most one bounded page for each visited draft before advancing the sequence cursor. At the end, start a new cycle from 0 with a fresh highwater. The known set in one cycle is finite, and late drafts join a later cycle without an unbounded visited set.

A transaction can allocate an earlier sequence and commit after a successor already advanced its scan cursor. The next complete cycle discovers that draft even when it committed behind the prior cursor. This is eventual, idempotent recovery. It does not establish one-shot startup completeness or database write fencing. Existing retained `HostOwnership.closed` is an abort/publication signal, not a transaction fence. The host rechecks ownership after asynchronous work, discards old authority publication, and repeats guard-owned recovery scans to catch late commits.

## Replay and cleanup

Publication can reveal an old journal sequence after a newer outcome was already delivered. After each checkpoint+receipt commit, query the OLDEST pending grants again. Do not retain an `after` journal frontier across publication cycles. Candidate IDs require the existing consistent `loadForRecovery` revision/receipt check before any numeric core apply. Existing 256 exact receipt capacity remains unchanged; apply/save bounded pages between reads, never apply all N and split a final state across receipt subsets.

Only after a complete seal, `cleanupVictimDraft(draftId,limit<=100)` deletes at most `limit` rows from each of credits, temporary visibility mappings and page proofs. Unsealed deletions fail closed at both API and SQL trigger boundaries. Once all temporary rows are gone, draft/source metadata is removed. Immutable published grants, existing checkpoint receipts and the constant-size outcome seal remain. New writes or a new draft for that sealed victim cannot reopen it. This cleanup does not choose a reset policy for abandoned, unearned live-victim contributions from a lost Area incarnation.

## Rollback and mixed-version deployment gate

Install the complete 007 rename, views, intent FK and insert guards in one migration transaction BEFORE enabling staging. Existing receipt FK/default/sequence/immutable trigger relation OIDs follow the physical table rename. New FKs target the physical relation; PostgreSQL cannot reference a view with a FK. The original-name filtered view preserves the tested original005 reader/writer SQL, including INSERT ON CONFLICT DO NOTHING, RETURNING and real FOR UPDATE row-lock behavior. Existing005/006 data remains unchanged. No new account character policy or public endpoint is added.

Physical INSERT guards require matching draft/victim/character/codec intent for a 007 victim. A guard on005 whole-manifest INSERT rejects coexistence with007 sources or permanent seals. The immutable007 seal continues blocking extra recipients or changed contents after temporary source/draft cleanup. Identical immutable grant retries remain allowed, and unrelated legacy opaque IDs retain their old behavior. This guard closes the mixed-version case where an old writer inserts a recipient that has not yet been staged and would otherwise become visible without a mapping.

All supported canonical old/new writers take the same sorted victim advisory lock before character or other row locks. SQL `world_victim_lock_key` uses the same SHA256 UTF-8 prefix and signed64 conversion as Node `victimAdvisoryLock`, without pgcrypto. Triggers reacquire this transaction lock as a backstop; they do not introduce a new host ownership epoch or fence. Direct database writers outside these supported transaction/lock contracts are not an additional application API.

The formal `contribution-rollback.test.mjs` suite executes an unchanged original first-PR68 CharacterStore fixture (7f48d43, source SHA256 pinned in the test) so shallow CI history does not weaken old-version coverage. Actual PostgreSQL cases include partial pending/recovery/save rejection, permanent cleanup gates, deferred FK failure, legacy non007 writers, semantic duplicate retries, row-lock contention, immutable triggers, canonical Unicode/signed key agreement and all four old005 versus007 begin/append race orders.

A pre007 connection executes the original named prepared SELECT and holds its transaction table lock while the actual007 migration waits for AccessExclusiveLock. After that read-only transaction commits, migration completes; the same backend and prepared query then exclude newly staged rows, and an original old save with a partial ID leaves revision unchanged. Previously committed partial receipts are not undone retroactively. Enabling staged writes before migration commit is outside this deployment contract.
