# 서버가 계산하는 공유 세계 설계

작성자: 로제 (2026-10-18). 브랜치 `design/server-world-20261017`, base `inhyk/dev` `1743cac`.

이 문서는 World of Crabcraft 를 "같은 지역에 있는 모든 사람이 같은 몬스터를 같이 잡는" MMORPG 로 바꾸는 계획이다. 세계는 서버가 계산하고(server-authoritative), 공개 세계 한 곳에 100명 정도가 들어간다. 아빠와 인혁이 쪽 에이전트(효연, 수영)가 같이 읽는다. 1장은 지금 코드가 어떻게 되어 있는지, 2장은 실제 게임 코드를 Node 에서 돌려 잰 숫자, 3장은 설계, 4장은 단계별 이전 계획, 5장은 아빠가 정할 것이다.

## 0. 결론

- 가능하다. 게임의 실제 클래스(`Player`, `abilities.ts`, `Combat`, `Enemy`, `Boss`, `Unit`, `QuestLog`)를 고치지 않고 Node 에서 돌렸다. 플레이어 100명과 적 100마리가 싸우는 월드 I 지역의 20 Hz tick 하나가 M4 Pro 에서 CPU 평균 0.29 ~ 0.43 ms, p99 0.7 ~ 1.4 ms 였다. 50 ms 예산의 1% 아래다. 지역 하나의 heap 은 5 MB 안팎이다.
- 비용은 CPU 보다 코드 구조에 있다. 첫째, 시뮬레이션이 three.js rig, 모션 클립 이벤트, VFX 콜백, HUD, "로컬 플레이어 한 명" 에 묶여 있다. 전투 핵심 파일 다섯 개(`combat.ts`, `abilities.ts`, `player.ts`, `enemies.ts`, `boss.ts`)에서 hud, vfx, audio, 카메라 흔들기, `g.player` 를 직접 부르는 곳이 180곳쯤 된다. 이것을 `src/sim/` 코어로 떼어 내야 한다. 둘째, 건물, 난파선 갑판, 부두, 등대 계단의 충돌체가 GLB 키트로 메시를 만드는 함수 안에서 등록된다. 서버에는 이것이 없어서 bake 단계가 필요하다. 셋째, XP, 코인, 퀘스트, 보스 클리어를 브라우저가 계산해서 저장하고 서버는 모양만 본다. 서버로 옮기면 캐릭터 저장 구조, 손님(guest) 처리, 기존 저장 이전을 정해야 한다.
- 네트워크: 지금 방(room) 방식(호스트 브라우저가 JSON 체크포인트 전체를 10 Hz 이상, 모든 플레이어가 자기 상태를 20 Hz 로 보냄)을 100명 지역에 쓰면 클라이언트 하나가 초당 500 ~ 680 KB 를 받는다(spike 실측). AOI(관심 반경) 60 m 와 양자화한 binary delta 로 바꾸면 10 Hz 기준 평균 2.6 ~ 3.5 KB/s, p95 3.7 ~ 7.1 KB/s 다. 지역 하나의 송신은 평균 0.3 MB/s 안팎이다.
- 이전은 9단계(S0 ~ S8)다. 단계마다 혼자 배포할 수 있고 게임은 계속 돈다. 사용자가 처음 체감하는 것은 S5(월드 I 공개 세계에서 같은 몬스터를 같이 잡기)이고, S1 ~ S4 는 화면에 드러나지 않는 준비다. 에이전트 작업량은 합쳐서 34 ~ 50일로 추정한다.

### 1.2 적, 스폰, AI, 어그로

- 스폰은 `game.ts` 의 `loadContent()` 가 정한다. Scrapling 무리 크기 `[3, 2, 2, 3, 2, 2]` 로 스폰 지점 6곳에 최대 12마리, 바닷가 얕은 물에 3마리, Scavenger 4마리, 바다에 Jellyfish 가 집을 찾은 만큼(지금 지형에서 5마리). 월드 I 의 보통 적은 24마리다. 그 밖에 월드 II 의 잔영 1마리와 보스 소환용 Scrapling 3마리가 숨어 있다.
- 상태는 `idle → chase → leash → idle`, 죽으면 `dead`(8초 뒤 가라앉기 시작, 9.6초에 숨김) 다음에 `stats.respawn`(월드 I 30 ~ 45초, 월드 II 12초)이 지나고 `canRespawnUnseen()` 이 참일 때 되살아난다. 이 검사는 "22 m 안에 플레이어가 없고, 이 브라우저의 카메라에 보이지 않거나 카메라에서 45 m 넘게 떨어져 있다" 이다.
- 어그로는 가장 가까운 플레이어 하나(`g.combatTarget()`)와의 거리가 `stats.aggro`(8.5 ~ 11 m) 안이고 높이 차가 3 m 안일 때 걸린다. 맞거나 무리 하나가 죽으면 무리 전체가 달려온다. 위협 수치(threat) 표는 없고 항상 가장 가까운 플레이어를 노린다.
- 레벨: 첫 보스를 깬 뒤나 월드 II 에서는 `scaleForJourney()` 가 적 레벨을 `max(기본 또는 10/20, partyLevel - 1)` 로 올린다. 방 안에서 가장 높은 플레이어 레벨에 맞춰진다.

### 1.3 피해, 능력, 쿨다운, 버프

- 맞는 순간: `Unit.act(id, { onHit })` 이 클립을 틀고, 클립의 `hit` 이벤트나 예비 타이머(`hitAt`, 없으면 클립의 hit 시각 + 0.1초)에서 `onHit` 이 불린다. 예비 타이머는 `Unit.updateVisual()` 이 줄인다. 클립 시각은 `src/motion/skills.ts` 와 `skillClips.ts` 의 순수 데이터라서 서버도 애니메이션 없이 같은 시각을 계산할 수 있다(spike 가 그렇게 돈다).
- 적의 할퀴기와 전사의 자동공격은 `onHit` 때 거리를 다시 본다(`gapTo` 2 m, `MELEE_GAP + 0.8`). 전사 능력(Pincer Strike, Shell Bash)은 대상이 살아 있는지만 본다.
- Bubble Bolt 와 마법사, 사제의 자동공격은 `vfx.projectile()` 의 구슬이 초속 17 ~ 22로 따라가다 닿을 때 피해가 들어간다. 대상이 도중에 죽으면 콜백은 불리지만 피해는 없다. Smite 는 바로 들어간다.
- 치명타는 `Math.random()` 12%(+보너스), 1.75배. 피해 배율은 `(1 + 0.12 × (레벨 - 1)) × (1 + 0.08 × 강화 단계)`.
- 상태이상은 `Unit` 의 필드다: stun, slow(비율), rust 중첩(중첩당 이동 10% 감소), absorb(Barnacle Ward), blessing(달샘 재생), push(밀치기, 끌어당기기).
- 쿨다운, GCD, 자원, 맞으면 시전이 밀리는 것(pushback), 0.4초 안에 누른 능력 예약은 모두 `Player` 에 있다.
- `Combat.damage()` 의 예외: 마을 놀이 중에는 피해 없음, 월드 III 레벨 잠금(100 미만은 솔라칸과 서로 피해 없음), 무적 디버그, absorb 먼저 깎기, 전사는 때릴 때 분노, 휘두르는 중이 아니면 맞는 동작.

### 1.4 보스

- 프로필 4개: 코로디우스(3레벨, HP 1300), 네레이드(10, 2600), 아스트라(20, 6200), 솔라칸(100, 180000). 상태는 `dormant → waking(2.4초) → idle → fight → dying → dead`.
- HP 60%, 25% 에서 2단계, 3단계(솔라칸은 75%, 40%). 단계마다 기술 순서표가 있고, 기술 하나는 1.1 ~ 3.1초(× tempo)의 경고 뒤에 터진다. 피해는 플레이어 최대 HP 의 비율이다(코로디우스 slam 26%, 솔라칸 slam 50%). 터지는 순간 모양 안에 있는 참가자(`combatPlayers()`)가 맞는다. 솔라칸은 참가자마다 100레벨을 요구한다.
- leash: 대상이 죽거나 경기장 밖 30 m 를 4초 넘게 벗어나면 초기화.
- 죽으면 안에 갇혀 있던 게가 걸어 나와 바다로 들어가는 연출, 마지막 보스 뒤에는 엔딩이 이어진다.
- 깨우기: 월드 I 은 등대를 켜야 하고 partyLevel 이 보스 레벨 이상이어야 한다. 도전 버튼은 플레이어를 경기장으로 옮긴다.
- 네트워크용 `BossState`(state, phase, enraged, timeline, mech{id, kind, at, yaw, left})가 이미 있다.

### 1.5 퀘스트, XP, 전리품, 코인

- XP: 적 처치(`stats.xp`, 혼자 할 때는 나, 방에서는 죽음 이벤트를 받은 모든 사람), 퀘스트 완료(`def.xp`), 보스 첫 클리어(`profile.reward`), 첫 보스 이후 5마리마다 순찰 보상(`180 + 50 × 레벨`). 20레벨 위로는 공식으로 끝없이 오른다.
- 코인: 적 처치 `max(5, xp / 4)`, 항해 섬 보물(업적과 함께). 대장간에서 `100 × (단계 + 1)` 코인으로 공격 강화(+8%).
- 전리품은 퀘스트 아이템 "Rusted Cog" 하나뿐이다. q1 진행 중 Scrapling 처치 때 70%, 두 번 연속 실패하면 확정. `setTimeout` 450 ms 뒤에 들어온다.
- 퀘스트 목표는 `quests.bump(kind)` 로 센다. kind 는 처치(kill-scrapling, kill-scavenger), collect-cog, beacon(등대 켜기), deliver(NPC 와 대화), 보스 처치, 월드 II 수정과 등불 모으기, deliver-supplies 다.

### 1.6 세계 이동

한 `Game` 이 챕터 1, 2, 3 을 모두 가진다. `world2.go()` 가 세계 함수를 갈아 끼우고, 같은 적 24마리를 새 집으로 옮기고 이름을 바꾼다. 주민도 옮긴다. 보스는 챕터마다 따로 있다. 이동 조건은 플래그다(네레이드 클리어 후 월드 II, 아스트라 클리어 후 월드 III). 공개 세계는 챕터별로 shard 가 나뉜다(`W1xxxx`, `W2xxxx`, `W3xxxx`).

### 1.7 지금의 멀티플레이

- `server/rooms.ts`: `ws` 위의 JSON 중계. 메시지는 enter, create, join, leave, state, action, world, combat, chat. 초당 60개(호스트는 240개) 제한, 메시지 최대 64 KB, 보낼 버퍼가 256 KB 를 넘으면 끊는다.
- 공개 shard(`enter`): 함께 있는 모습과 채팅만 나눈다. 전투 권한자가 없어서 적은 사람마다 따로다. 정원 8명, 가장 덜 찬 shard 로 들어간다.
- 코드 방(`create`/`join`, 6자리 코드, `combatVersion 1`): 처음 들어온 전투 멤버가 호스트다. 호스트 브라우저가 모든 적 AI 와 보스를 돌리고 `world` 체크포인트(`WorldState`)를 0.1초마다, 그리고 공격과 죽음마다 보낸다. 손님은 그 위치로 부드럽게 따라간다(`k = 1 - exp(-25 dt)`). 손님이 때리면 `attack{target, amount, crit, rage}` 를 보내는데 피해량 `amount` 를 손님이 계산한다. 호스트는 거리(38 m)만 보고 그대로 적용한다. 손님의 stun, slow, push 는 범위가 제한된 `condition` 으로 보낸다. 호스트가 나가면 남은 전투 멤버 중 첫 사람이 마지막 체크포인트에서 이어받는다(`resumeAuthority`). 빈 방의 체크포인트는 24시간 남는다.
- 모든 플레이어가 자기 상태(x, y, z, yaw, hp, maxHp, alive, level)를 20 Hz 로 보낸다. 위치 권한이 브라우저에 있고 서버는 숫자가 유한한지만 본다.
- `worldOf()` 는 엔티티 128개가 넘는 체크포인트를 거절한다.
- spike 로 잰 크기: 월드 I 체크포인트 JSON 은 엔티티 47개(적 24, NPC 와 주민 15, 숨은 보스와 풀려나는 게 8)에서 10.5 KB 다. 실제 게임은 숨은 잔영과 소환용 Scrapling 까지 51개라 조금 더 크다. 손님 한 명이 최소 초당 100 KB 를 받는다. 상태 메시지 하나는 205 B 쯤이다.

### 1.8 저장

- `BossJourney.save()` 가 3초마다, 그리고 사건마다 localStorage 키 `cc.journey.v1:<race>:<sex>:<class>:<name>` 에 쓴다. 들어가는 것: xp, coins, attackRank, quests, objectives, tracked, rust, abyss, trueCleared, finalCleared, firstEnding, moonwater, beacon, mood, chapter, kills, achievements.

- `002_google_only.sql` 주석에 따르면 2026-10-17 에 dev 에는 QA 계정만, prod 에는 계정이 없었다. 지금은 계정 저장을 옮기는 부담이 작다.

### 1.9 렌더링에 묶인 곳 (spike 를 돌리며 하나씩 부딪친 것)

1. `Unit` 은 rig 와 motion controller 를 가진다. 위치는 THREE.Object3D 다. spike 는 메시 없는 `THREE.Group` 으로 돌렸다.
2. 맞는 순간이 클립 이벤트와 `Unit.updateVisual()` 의 타이머에 있다. 서버도 매 tick 모든 유닛의 `updateVisual()` 을 불러야 피해가 들어간다.
3. 원거리 피해가 VFX 콜백(`vfx.projectile`) 안에 있다. spike 는 같은 유도 비행을 sim 쪽에 다시 짰다.
4. 전투 파일 다섯 개가 HUD 39곳, VFX 54곳, 소리 35곳, 카메라 30곳, `g.player` 20곳을 직접 부른다(grep 수). spike 는 대부분 아무것도 안 하는 Proxy 로 막았다.
5. 로컬 플레이어 한 명 가정: `Combat` 의 `g.player.onDamaged/gainRage/onWardHit`, `Enemy` 의 `g.player.lineOfSight`, `Boss.engage()` 의 `g.player.unit.blessingUntil`, `onUnitDied` 의 `this.player.gainXp`. spike 는 플레이어마다 `Object.create(game)` 으로 game view 를 하나씩 만들고, 피해를 맞는 사람의 view(또는 때린 사람의 view)로 보내는 router 를 붙였다.
6. sim 안의 카메라: `canRespawnUnseen()` 이 카메라 frustum 을 본다.
7. sim 안의 입력: `Player.update()` 가 키보드와 카메라 방향을 직접 읽는다.
8. `game.ts` 의 `setTimeout` 10곳(톱니 드롭 450 ms, 보스 깨우기 2.6초, 승리 배너, 퀘스트 이어 받기)은 게임 시간이 아니라 벽시계다.
9. 상태에 번역된 문자열이 들어간다(`unit.name = t(...)`). 서버는 id 를 보내야 한다.
10. 월드 II, III 은 세계 함수를 갈아 끼우고 같은 적을 옮긴다.
11. 충돌체 등록이 메시 생성 안에 있다.
12. `Math.random()` 을 씨앗 없이 쓴다. 서버가 권한자면 문제없다. 다만 브라우저가 피해나 치명타를 예측할 수는 없다(하지도 않는다).

## 2. Feasibility spike

### 2.1 무엇을 돌렸나

코드는 `server/sim/spike/`(`world.ts`, `sim.ts`, `snapshot.ts`, `main.ts`)와 `tools/sim-spike.mjs`, `tools/sim-spike-fanout.mjs` 에 있다. 배포되는 코드는 바꾸지 않았다.

```sh

node tools/sim-spike-fanout.mjs --clients 100 --bytes 400 --hz 10 --seconds 10
```

- 진짜 코드: `Player`(이동, GCD, 쿨다운, 시전, 자동공격, 자원, XP), `abilities.ts`, `Combat`, `Enemy`(배회, 어그로, 무리, 추격, 도약, leash, 재생성), `Boss`(코로디우스의 단계와 기술 전부), `Unit`, `QuestLog`, `Terrain`, `Collision`(지형 격자), `layout.ts` 스폰 데이터, `skills.ts` 시각. esbuild 로 Node 용으로 묶었다. `tests/run-boss.mjs` 가 이미 쓰는 방식이다.
- 바꾼 것: rig 와 motion controller 는 stub 이다. 클립 이벤트가 없으니 공격은 예비 타이머(`hitAt`, 없으면 클립 hit 시각 + 0.1초)에 맞는다. HUD, 소리, VFX 는 아무것도 안 하는 Proxy 이고, 투사체만 같은 유도 비행으로 다시 짰다. 입력은 bot 이다. 플레이어마다 game view 하나와 `Combat` 하나를 두고, 피해는 맞는 플레이어의 view 로 보낸다. 적 재생성은 기본값 `--respawn timed` 로 카메라 검사를 뺐다(타이머만).
- 없는 것: 건물, 난파선, 부두 충돌체(그래서 보스는 바닷가 모래밭에 세웠다), NPC 와 주민, 월드 II, III, 채팅, 실제 네트워크(송신 비용은 2.4절에서 따로 쟀다), 입력 파싱.
- bot: 45 m 안의 가장 가까운 적을 잡고, 전사는 1.2 m, 마법사와 사제는 12 m 까지 걸어간 뒤, 0.4초마다 능력 1 ~ 4번을 차례로 누른다. 자동공격은 `Player` 가 한다. 레벨은 보통 3, 보스 시나리오는 5.
- 시나리오:
  - `normal`: 월드 I 의 적 24마리 그대로(재생성 30 ~ 45초).
  - `dense`: 플레이어 1명당 적 1마리가 되도록 무리를 집 근처에 복사, 재생성 6초.

- snapshot 을 20 Hz 로 보내도 하나의 크기는 비슷했다(normal 100명 AOI 60 m 평균 319 B, dense 256 B). 초당 바이트가 두 배가 된다.
- 피해 숫자, 시전, 죽음 같은 사건은 표에 없다. 2.2절의 사건 수에 binary 사건 하나 6 ~ 8 B 를 곱하면 보스전처럼 모두가 서로를 볼 때 클라이언트당 1 ~ 2 KB/s 가 더 든다(추정). JSON 사건(80 B 안팎)이면 그 10배다.

### 2.4 WebSocket 송신 비용

`tools/sim-spike-fanout.mjs`: 서버 프로세스가 `ws`(게임 서버와 같은 패키지)로 클라이언트 100개에 메시지를 보내고, 다른 프로세스가 받은 개수를 센다. 받은 수는 보낸 수와 같았다.

| 메시지 크기 | 송신 빈도 | 서버 송신량 | 서버 프로세스 CPU (코어 하나 대비) |
|---|---|---|---|
| 400 B binary | 10 Hz | 343 KB/s | 1.9% |
| 700 B binary | 20 Hz | 1.28 MB/s | 3.4% |
| 4000 B binary | 10 Hz | 3.88 MB/s | 0.9% |
| 22000 B text | 10 Hz | 21.3 MB/s | 1.3% |

이 크기에서는 메시지 크기보다 메시지 수가 CPU 를 정한다. 같은 부하 아래에서 잰 값이라 ±1%p 쯤 흔들린다.

### 2.5 spike 가 말해 주지 않는 것

- e2-medium vCPU 가 M4 Pro 코어보다 몇 배 느린지는 재지 않았다. 3.7절은 2 ~ 4배로 가정했다. S4 에서 bot 100개로 dev VM 에서 직접 잰다.
- 충돌체가 지형뿐이라 `resolveCollision` 이 실제보다 싸다(실제는 건물과 소품 수백 개가 공간 해시에 들어간다).
- 입력 처리, 진행 저장(DB 쓰기), 채팅, 주민과 NPC 를 넣지 않았다.
- stub motion 때문에 `hitAt` 이 없는 공격(적의 할퀴기, 전사 능력 등 대부분)이 클립의 실제 hit 보다 0.1초 늦게 맞는다.

```
| PlayerSim 예측 (src/sim)     |                 |   src/sim: 유닛, 적, 보스, 전투,  |
| 보간 버퍼 약 120 ms          | <-------------- |   퀘스트, XP                      |
| three.js, HUD, 소리, 카메라  |  snapshot 10 Hz |   AOI 격자 -> 클라이언트별 delta  |
+------------------------------+  + 사건         |   진행 -> Postgres                |
                                                 +-----------------------------------+
```

- 지역(area) 하나를 고정 tick(20 Hz)으로 서버가 돌린다. 지역은 월드 I, II, III 과 보스 인스턴스다. 한 지역이 100명을 넘으면 같은 지역의 shard 를 하나 더 연다(W1 shard 2).
- 브라우저는 intent(이동 방향, 점프, 달리기, 바라보는 방향, 대상, 능력 슬롯, 상호작용)만 보낸다. 피해량, 위치, XP 는 보내지 않는다.
- 서버는 snapshot(AOI 안 엔티티의 달라진 필드)과 사건(피해, 회복, 죽음, 시전 시작, 시전 끊김, 능력 결과, 보스 기술 시작, XP, 레벨, 코인, 전리품, 퀘스트 진행, 채팅, 동작)을 보낸다.
- 새 WebSocket 경로 `/world` 를 binary 프레임으로 연다. `/multiplayer` 중계는 옛 화면을 위해 이전이 끝날 때까지 그대로 둔다(AGENTS.md 의 서버 규칙).

### 3.2 tick, snapshot, 보간, 예측

- tick 20 Hz(50 ms). 지금 플레이어 상태가 20 Hz 로 나가고, 보스 기술의 가장 짧은 경고가 1.1초라 50 ms 해상도면 충분하다. tick 루프는 `setTimeout` 대신 다음 tick 시각을 누적해 밀림을 보정한다.
- snapshot 10 Hz. 2.3절에서 20 Hz 로 보내도 하나의 크기가 비슷해서 초당 바이트만 두 배가 된다. 다른 엔티티는 서버 시각보다 약 120 ms 뒤를 그린다(snapshot 간격 100 ms + 흔들림 여유). 자기 자신의 기록에는 마지막으로 처리한 입력 번호(seq)를 붙인다.
- AOI: 화면에서 유닛을 숨기는 거리(`CULL_DIST` 80 m)에 맞춰 들어올 때 80 m, 나갈 때 88 m 로 시작한다. 2.3절에서 60 m 보다 바이트가 1 ~ 24% 많을 뿐이다. 대역폭이 모자라면 60 m 로 줄이고 들어올 때 서서히 나타나게 한다. 자기 자신, 파티원, 지금 대상, 싸우는 보스는 반경과 관계없이 넣는다. 지역마다 16 m 격자로 엔티티를 나눠 두면 반경 검색이 엔티티 전부를 도는 것보다 싸다(spike 는 전부를 돌았다).
- 자기 이동 예측: 키를 누르면 `src/sim` 의 같은 이동 코드(`Player.update()` 의 가속, 뒷걸음, 달리기, 충돌)로 바로 움직이고 입력을 seq 와 함께 보관한다. 서버가 seq 와 위치를 확인해 주면 그 위치에서 아직 확인되지 않은 입력을 다시 적용한다. 차이가 작으면 100 ms 동안 부드럽게 맞추고, 2 m 넘으면 바로 옮긴다. 밀치기와 끌어당기기는 서버 사건으로만 적용한다. 예측이 맞으려면 브라우저와 서버의 충돌이 같아야 한다(S3 의 일치 검사).
- 지연 숨기기:
  - 능력: 누르는 순간 브라우저가 같은 규칙(GCD, 쿨다운, 자원, 사거리, 시야)으로 먼저 검사하고, 휘두르는 동작이나 시전바를 바로 시작하고 `ability{slot, target, seq}` 를 보낸다. 서버가 받아들이면 `castStart`, 거절하면 `abilityResult{seq, 이유}` 를 보내고 브라우저는 동작을 멈추고 이유를 띄운다.
  - 맞음 확인: 근접은 휘두른 뒤 0.28 ~ 0.38초에 맞는다(`skills.ts`). 국내 VM(asia-northeast3)이라 왕복 지연이 수십 ms 안쪽이면(미측정) 서버의 `damage` 사건이 휘두르는 동작이 닿는 즈음에 도착한다. 피해 숫자와 맞는 동작은 서버 사건이 왔을 때 띄운다.
  - 원거리: 투사체 비행은 서버가 계산하고, 브라우저는 시전이 끝나는 순간부터 구슬을 그린다. 닿는 순간은 서버 `damage` 사건에 맞춘다.
  - 보스 경고: 서버가 기술 시작 사건에 "터지는 서버 tick" 을 넣는다(지금 `mech.left` 와 같다). 브라우저는 서버 시계(환영 메시지의 서버 시각과 왕복 지연으로 맞춘다)로 남은 시간을 그린다. 판정은 터지는 tick 의 서버 위치로 한다. 경고가 1.1초 이상이라 수십 ms 차이는 피하는 데 지장이 없다.
  - 쿨다운 표시는 예측으로 돌리고 서버 값으로 고친다.

### 3.4 코드 공유: `src/sim/`

- 서버와 브라우저가 같이 쓰는 규칙과 데이터를 `src/sim/` 으로 모은다: 직업과 능력 데이터, `ENEMY_STATS`, `BOSS_PROFILES`, XP 표, 퀘스트 정의(번역 문장은 브라우저에), 이동 적분, 지형과 bake 한 충돌 질의, 능력 시각 데이터, 적과 보스 AI, `Combat` 규칙, 지역(Area) 클래스.
- `src/sim/` 은 `three`, DOM, `src/ui`, `src/core`, `src/crab`, `src/motion`(시각 데이터는 `src/sim/data` 로 옮긴다)을 import 하지 않는다. 엔티티 상태는 숫자 필드(x, y, z, yaw)로 둔다. snapshot 만들기가 쉽고 GC 가 줄어든다. 테스트 하나가 import 를 검사한다.
- sim 은 바깥을 부르지 않고 사건을 낸다(`damage`, `heal`, `death`, `castStart`, `projectile`, `telegraph`, `say`, `levelUp`, `error`). 브라우저는 사건을 지금의 HUD, VFX, 소리 호출로 바꾸는 sink 를 단다. 혼자 하기(오프라인)는 브라우저가 Area 를 직접 돌리고 같은 sink 를 쓴다.
- 시간은 sim 의 게임 시간만 쓴다(`setTimeout` 금지). 난수는 sim 에 함수로 넘긴다(테스트에서 씨앗을 고정).
- 서버는 `server/node/build.mjs`(esbuild)가 `src/sim` 을 `server-dist/main.mjs` 에 같이 묶는다. 지금 빌드 방식 그대로 된다.

### 3.5 진행 권한

- 서버가 계산하고 저장한다: XP, 레벨, 코인, 공격 강화, 전리품, 퀘스트 상태와 목표 수, 보스 클리어, 챕터 해금, 달샘 축복, 업적, 보물, 마지막 지역과 위치.
- 저장 구조(Postgres): `characters(id, owner_account, guest_token_hash, spec jsonb, xp, level, coins, attack_rank, quests jsonb, objectives jsonb, bosses jsonb, chapter, flags jsonb, achievements jsonb, area, x, z, revision, updated, created)`. 쓰기 시점은 레벨업, 퀘스트 완료, 보스 클리어, 구매 같은 사건과 10초마다, 연결이 끊길 때, 서버가 꺼질 때.
- 브라우저의 저장 묶음에서 이 필드들을 뺀다. 계정 저장(`/api/account/save`)에는 꾸밈과 설정만 남긴다. 그때까지 옛 화면이 보내는 진행 값은 서버 세계에 쓰지 않는다.
- 손님(로그인 없이): 지금처럼 바로 놀 수 있어야 한다(아이들이 주 사용자). 추천은 서버 쪽 손님 캐릭터다. 브라우저가 무작위 32바이트 손님 토큰을 localStorage 에 두고, 서버는 그 해시로 캐릭터를 찾는다. 30일 동안 안 쓰면 지운다. Google 로그인을 하면 그 손님 캐릭터를 계정으로 옮긴다. IP 당 손님 만들기 속도를 제한한다. DB 가 안 되면 메모리에만 있는 임시 손님으로 들어가게 한다.
- 기존 저장 이전: 서버 세계에 처음 들어올 때 이 기기의 `cc.journey.v1:*` 저장(계정이면 이미 서버 `accounts.save` 에 있는 묶음)을 한 번 가져와 캐릭터를 만든다. 서버가 값을 검사한다(플래그 순서가 맞는지: abyss 는 rust 다음, 챕터는 해금 플래그와 맞는지, 퀘스트 목표 수 범위). XP 와 코인을 그대로 믿을지는 5장 결정 2 다. 2026-10-17 기준 prod 계정이 없어서 지금이 옮기기 가장 싼 때다.

### 3.6 코드 방, 8명 정원, 호스트 선출

- 지금 코드 방이 하는 일: 친구끼리 한 세계(보스, 챕터 이동, 등대, 파티, 협동/싸우기 모드, 마을 놀이, 배)를 나눈다. 정원 8명이고 호스트 브라우저가 계산한다.
- 바뀐 뒤:
  - 파티: 공유 세계 안에서 6자리 코드로 파티를 만든다. 코드로 들어오면 파티장의 지역 shard 로 옮겨 준다. 파티원은 AOI 와 관계없이 보이고, 처치 보상과 퀘스트 진행을 나눈다(5장 결정 4).
  - 이야기 보스(코로디우스, 네레이드, 아스트라, 솔라칸)는 파티 인스턴스로 연다. 파티가 도전하면 서버가 경기장만 있는 작은 지역을 만들고 파티원(최대 8명)을 옮긴다. 지금의 난이도 조정, 죽음 연출, 엔딩이 그대로 맞는다. 100명이 한 보스를 몰아치는 것도 막는다. 공유 세계에 나타나는 월드 보스는 나중에 따로 만들 수 있다.
  - 호스트 선출(`battle.ts`), 손님이 보내는 피해량, 체크포인트 중계는 보스 인스턴스가 돌고 나면(S7) 없앤다. 그때까지 코드 방은 옛 길로 계속 돈다.
  - 마을 놀이와 배는 서버 기능으로 옮기거나 S7 에서 정리한다(5장 결정 7).

### 3.7 용량

100명 지역 하나의 비용(2장 실측, e2-medium 은 2 ~ 4배 느리다고 가정한 추정):

| 항목 | M4 Pro 실측 (코어 하나 대비) | e2-medium 추정 (vCPU 하나 대비) |
|---|---|---|
| sim tick 20 Hz | 0.29 ~ 0.43 ms/tick, 0.6 ~ 0.9% | 1.2 ~ 3.4% |
| snapshot 인코딩 10 Hz (binary, AOI 60 m, 100명) | 1.3 ~ 2.7 ms, 1.3 ~ 2.7% | 2.6 ~ 10.8% |
| WebSocket 송신 100명 10 ~ 20 Hz | 1.9 ~ 3.4% | 3.8 ~ 13.6% |
| 입력 파싱, 진행 저장 | 미측정 | 미측정 |
| 합계 | 약 4 ~ 7% | 약 8 ~ 28% |

- e2-medium 은 shared-core 라 오래 쓸 수 있는 것은 vCPU 하나 정도이고 짧게 두 개까지 올라간다(GCP 문서 기준, 확인 권장). 같은 VM 에 Postgres, Caddy(TLS), dev 와 prod 서버가 같이 돈다.
- 메모리는 문제가 안 된다. 지역 하나가 heap 수 MB 와 지형 배열 3.3 MB 이고, Node 프로세스 기본이 50 ~ 80 MB 다. 4 GB 에 여유가 크다.
- 대역폭(10 Hz, AOI 60 m, binary):

| | 클라이언트 하나 | 100명 지역 하나 |
|---|---|---|
| 지금 방식 JSON (실측) | 500 ~ 680 KB/s | 50 ~ 68 MB/s (불가능) |
| binary delta, AOI 없음 | 5.4 ~ 6.7 KB/s | 0.54 ~ 0.67 MB/s |
| binary delta, AOI 60 m | 평균 2.6 ~ 3.5 KB/s, p95 3.7 ~ 7.1 KB/s | 평균 0.26 ~ 0.35 MB/s |
| 사건 (추정) | 1 ~ 2 KB/s | 0.1 ~ 0.2 MB/s |
| 모두 계속 움직일 때 상한 (계산) | 13.5 KB/s | 1.35 MB/s |

  100명 지역이 하루 종일 가득 차 있으면 송신이 시간당 1.8 GB 쯤이다(0.5 MB/s 기준). 실제 평균 접속자는 훨씬 적다. GCP 송신 요금은 확인해서 정한다.
- 예산과 승격 기준:
  - 처음(S5): prod 의 공개 세계 지역 하나를 기존 Node 프로세스 안에서 돌린다. 빈 지역은 tick 을 멈춘다. dev 도 사람이 없으면 멈추므로 prod 에 CPU 를 거의 쓰지 않는다.
  - 지표: tick p99 가 VM 에서 10 ms(예산의 20%)를 넘거나, VM CPU 가 10분 평균 60% 를 넘거나, prod 동시 접속이 100명을 넘으면 다음 단계로 간다.
  - 다음: e2-standard-2(전용 vCPU 2개, 8 GB)로 올리고, 지역마다 `worker_threads` 하나씩 두어 코어 두 개를 쓴다. dev 는 따로 작은 VM 으로 옮기거나 쓸 때만 켠다.
  - 그 다음(동시 300명 이상): 지역을 여러 프로세스나 VM 으로 나누고, 입장 서버가 지역별 주소를 알려 준다.

### 3.8 재접속, 배포 재시작, 부정행위 방지

- 재접속: 환영 메시지에 재개 토큰(60초 유효)을 준다. 연결이 끊겨도 서버는 캐릭터를 15초 동안 지역에 남긴다(바로 사라지지 않게). 그 안에 돌아오면 같은 엔티티로 이어 가고, 지나면 저장된 위치에서 다시 들어간다. 브라우저 재시도는 지금의 1.5초 5번에서 지수적으로 늘려 30초까지 간다.
- 배포 재시작: 지금 `activate.sh` 는 dev 나 main 에 머지될 때마다 서버를 다시 띄워서 연결이 모두 끊긴다. 바꾼 뒤:
  - 지역은 `crabcraft-world@<env>` 라는 별도 systemd 유닛으로 돌린다. 계정, 웹, 중계만 바뀐 배포는 세계를 건드리지 않는다.
  - SIGTERM 을 받으면 입력을 막고, 모든 캐릭터 진행을 저장하고, "서버 점검" 사건을 보낸 뒤 끝난다(지금 `TimeoutStopSec=15` 안에). 브라우저는 재개 토큰으로 다시 붙어 저장된 위치에 선다.
  - 적의 위치와 HP 는 저장하지 않는다. 지역은 처음 상태로 다시 시작하고 적은 금방 재생성된다. 진행 중이던 보스 인스턴스는 잃는다(벌칙 없이 다시 도전). 필요해지면 지역 상태를 30초마다 Postgres 에 남기는 것을 나중에 붙인다.
- 부정행위 방지 기본:
  - 브라우저는 intent 만 보낸다. 이동 intent 는 -1 ~ 1 로 자르고, 속도는 서버 이동 코드가 정한다. 순간이동과 빠른 이동이 원리적으로 안 된다.
  - 쿨다운, GCD, 자원, 사거리, 시야, 대상 유효성, 시전 중 이동을 서버가 검사한다. 거절한 수를 세서 기록한다.
  - 피해량, XP, 코인, 전리품을 서버가 계산한다(지금 코드 방 손님은 피해량을 직접 보낸다).
  - 메시지 종류별 속도 제한(지금 초당 60개 전체 제한에 더해 능력은 초당 10개 같은 것), 메시지 크기 제한, binary 디코더의 범위 검사.
  - 채팅은 지금처럼 제어 문자를 지우고 0.7초 간격 제한을 둔다. 낯선 사람이 많아지므로 차단, 신고, 필터가 필요하다(5장 결정 9).

### S1. sim 출력 분리

- 할 일: `Combat`, `abilities.ts`, `Player`, `Enemy`, `Boss` 가 hud, vfx, audio, follow 를 부르는 대신 사건을 낸다. 브라우저 sink 가 사건을 지금의 호출로 바꾼다. `Combat` 은 플레이어 반응(onDamaged, gainRage, onWardHit)을 맞은 유닛의 controller 로 보낸다. 투사체 비행을 sim 으로 옮기고 VFX 는 그리기만 한다. 맞는 순간은 클립 이벤트 대신 `skills.ts` 의 시각으로 정하되 지금 클립의 hit 시각과 같게 한다(예비 타이머의 +0.1초를 쓰지 않는다). `setTimeout` 을 게임 시간 타이머로 바꾼다. `Enemy` 의 시야는 대상 플레이어 기준으로, `canRespawnUnseen` 의 카메라 검사는 "근처 플레이어 없음" 으로.
- 검사: `pnpm build`, `pnpm test:boss`, `pnpm test:engine`, `pnpm test:multiplayer`, 새 `tests/sim-*.test.mjs`(spike 의 하네스를 테스트로: 기록 sink 로 진짜 클래스를 돌려 피해, 처치, XP, 쿨다운 거절, 보스 기술 명중과 빗나감을 확인), `node tools/playtest.mjs`, 두 브라우저로 코드 방(호스트 권한이 그대로 도는지).
- 인혁이 쪽이 피할 것: `src/game/{combat,abilities,player,enemies,boss,unit}.ts`, `src/multiplayer/battle.ts`. 새 능력이나 새 적을 넣는 일은 S1 이 머지된 뒤로.

### S2. `src/sim/` 코어

- 할 일: `SimUnit`(숫자 필드)과 view(rig, motion, 이름표)를 나눈다. `Player` 를 `PlayerSim`(intent → 이동과 전투)과 `PlayerInput`(키보드와 카메라 → intent)으로 나눈다. `Area` 가 한 지역의 유닛, 적, 보스, 투사체, 타이머를 가진다(로컬 플레이어 가정 없음). 월드 II, III 은 적을 옮기지 않고 자기 적 목록을 가진 지역 정의가 된다. 혼자 할 때는 브라우저가 `Area` 를 돌린다. `src/sim` import 규칙 테스트.
- 검사: S1 의 검사 전부, `src/sim` 을 Node 에서 바로 돌리는 테스트(씨앗 고정 난수로 같은 결과), 월드 II, III 왕복 이동 플레이테스트.
- 인혁이 쪽이 피할 것: `src/game` 의 전투와 AI 파일 전부, `world2.ts` 와 `world3.ts` 의 적과 NPC 부분, `npcs.ts`.

### S3. 충돌 bake

- 할 일: 충돌체 등록을 키트 없이 부를 수 있게 떼어 낸다. 건물 상자, 난파선 갑판 다각형, 부두, 등대 계단은 대부분 `layout.ts` 상수에서 나온다. 걸을 수 있는 면은 `rectSurface`, `annulusSurface`, `polySurface` 의 인자로 기록한다. 떼어 내기 어려운 곳은 Playwright 로 실제 세계를 만든 뒤 등록 호출을 기록해 `public/world/collision-w1.json` 같은 파일로 내보낸다. 월드 II(`world2Settlement.ts`), III(`world3.ts`)도 같게.
- 검사: Playwright 로 실제 브라우저 세계에서 격자 1만 점의 `heightAt`, `resolveCollision`, `raycastSolid` 를 뽑아 Node 의 bake 세계와 비교한다(차이 1e-6 아래). layout 파일이 바뀌었는데 bake 가 낡았으면 CI 가 실패하게 한다.
- 인혁이 쪽이 피할 것: `src/world/` 의 충돌 코드(`collision.ts`, `buildings.ts`, `wreck.ts`, `lighthouse.ts`, `dressing.ts`, `foliage.ts`, `fountain.ts`), `layout.ts`, `terrain.ts`, `world2Settlement.ts`, `world3.ts`, `dawnScenery.ts`. S3 뒤로는 충돌을 바꾸면 bake 를 다시 만든다.

### S4. 서버 지역과 프로토콜 v2

- 할 일: `server/world/` 에 지역 호스트(20 Hz 루프, 밀림 보정), 클라이언트별 입력 큐, AOI 격자, binary snapshot 과 사건 인코더(spike 의 `ClientView` 에서 시작), 손님 토큰으로 캐릭터 붙이기(진행 저장은 아직 메모리), `/world` 경로, 지표(tick p50, p99, 넘친 tick 수, 보낸 바이트). bot 라이브러리와 `tools/load-world.mjs`(WebSocket bot 100개가 intent 를 보냄). 빈 지역은 멈춘다.
- 검사: `server/world/*.test.mjs`(node --test), 로컬과 dev VM 에서 bot 100개 부하 시험. 여기서 e2-medium 의 실제 tick p99 와 CPU 를 잰다(3.7절의 가정을 고친다). 잘못된 입력 fuzz.
- 인혁이 쪽이 피할 것: `server/node/main.ts`. `server/rooms.ts` 는 이 단계에서 건드리지 않는다.

### S5. 월드 I 공개 세계를 서버 세계로

- 할 일: 월드 I 공개 shard 를 `/world` 로 바꾼다. 처음에는 `?world=server` 로 켜고, 시험이 통과하면 기본값으로 한다. 브라우저는 intent 를 보내고, 서버 엔티티를 보간해 그리고, 자기 이동을 예측하고 맞추고, 능력 동작을 먼저 시작하고, 서버가 확인한 피해와 처치를 띄운다. 적, 전투, XP, 코인, 톱니, 처치 퀘스트를 서버가 계산해 사건으로 보낸다. 진행 저장은 아직 브라우저가 하지만 값은 서버 사건에서 온다. shard 정원을 8 → 25 → 50 → 100 으로 시험을 통과할 때마다 올린다. 혼자 하기와 코드 방은 옛 길 그대로. `/world` 가 안 되면 옛 공개 shard 로 돌아간다. 재접속 토큰을 이 단계에서 넣는다.
- 검사: 두 브라우저 Playwright(둘이 같은 Scrapling 을 때리면 HP 가 같다, 처치 보상 규칙, 끊었다 다시 붙기), 지연을 넣는 WebSocket 프록시(100 ms, 200 ms)로 예측과 맞추기 확인, dev VM 에서 bot 100개 + 실제 브라우저 2개, `node tools/playtest.mjs`.
- 인혁이 쪽이 피할 것: `src/multiplayer/*`, `game.ts` 의 frame loop 와 입력, `player.ts`, HUD 의 액션바와 시전바, 미니맵의 엔티티 그리기.

### S6. 진행 권한을 서버로

- 할 일: 3.5절의 `characters` 테이블과 마이그레이션, 서버가 모든 보상(처치, 퀘스트, 보스, 순찰, 대장간, 보물)을 계산하고 저장, 손님 캐릭터, 로그인 때 손님 캐릭터 옮기기, 기존 저장 가져오기, 같은 캐릭터로 두 창이 들어오면 앞의 것을 내보내기, 끌 때 저장. 월드 II, III 은 S7 전까지 브라우저 계산이므로 그 동안은 서버가 분당 XP 상한 같은 그럴듯함 검사를 한다.
- 검사: 서버 진행 테스트(보상, 레벨업, 퀘스트 흐름), 저장 가져오기의 경계 사례, 두 창, SIGTERM 때 저장되는지.
- 인혁이 쪽이 피할 것: `server/node/accounts.ts`, `server/node/migrations/`, `src/account.ts`, `src/accountStorage.ts`, `bossJourney.ts` 의 저장과 복원.

### S7. 월드 II, III, 보스 인스턴스, 파티

- 할 일: 월드 II, III 지역을 서버로. 이야기 보스를 파티 인스턴스로(3.6절). 파티 코드와 파티 보상. 호스트 선출과 손님 피해량 경로를 없애고, `/multiplayer` 는 옛 화면을 위해 정한 기간 동안 중계만 남긴 뒤 없앤다. 마을 놀이와 배를 서버 기능으로 옮기거나 정리한다.
- 검사: 인스턴스 수명(파티 도전 → 인스턴스 → 승리 → 클리어 저장 → 복귀), 월드 III 레벨 잠금(캐릭터마다), 두 브라우저 파티 보스전, bot 100개 + 인스턴스 여러 개.
- 인혁이 쪽이 피할 것: `boss.ts`, `bossJourney.ts`, `world2.ts`, `world3.ts`, `villageGames.ts`, `shoreBoat.ts`, `src/multiplayer/battle.ts`, `server/rooms.ts`, `server/combatProtocol.ts`.

### S8. 운영

- 할 일: `crabcraft-world@<env>` 유닛과 `activate.sh` 수정(세계 코드가 바뀐 배포만 세계를 다시 띄움), 끌 때 순서(입력 막기, 저장, 알림), 지표를 보는 길(로그 또는 `/healthz` 확장), 메시지 종류별 제한, 거절 기록.
- 검사: 플레이 중 `systemctl restart` 했을 때 진행이 남고 다시 붙는지, 웹만 바뀐 배포에서 세계 연결이 안 끊기는지.
- 인혁이 쪽이 피할 것: `deploy/vm/*`, `.github/workflows/deploy.yml`, `server/node/main.ts`.

## 5. 위험과 아빠가 정할 것

### 위험

1. S1, S2 는 전투 파일 전체를 고친다. 인혁이 쪽이 같은 파일에 기능을 넣으면 충돌한다. 단계마다 피할 파일을 정하고, PR 을 작게 나눠 빨리 머지한다.
2. 리팩터링이 손맛을 바꿀 수 있다(맞는 순간, 이동 가속). spike 의 하네스를 회귀 테스트로 쓰고 플레이테스트로 확인한다.
3. bake 한 충돌이 브라우저와 다르면 예측한 위치가 자꾸 되돌려진다. S3 의 일치 검사로 막는다.
4. VM 성능은 아직 모른다. spike 는 부하가 심한 M4 Pro 에서 쟀다. S4 에서 VM 으로 잰 뒤에 정원과 승격 시점을 확정한다.
5. Node 이벤트 루프 하나에 계정, 중계, 지역이 같이 돈다. 느린 DB 질의나 큰 GC 가 tick 을 밀 수 있다. 지역을 `worker_threads` 로 나누면 풀린다.
6. 공유 세계의 균형: 사냥감 부족(2.2절), 처치 보상 규칙, 레벨 스케일, 보스 몰아치기.
7. 옮기는 동안 옛 길(`/multiplayer` 의 손님 피해량, 브라우저 진행 저장)이 남아 있어 그쪽으로는 여전히 속일 수 있다. S6, S7 에서 닫는다.
8. 아이들이 낯선 사람 100명과 한 세계에 있게 된다. 채팅과 괴롭힘 대책이 필요하다.
9. 접속자가 늘면 송신량과 요금이 는다.
10. dev 는 PR 이 머지될 때마다 다시 배포되어 시험하는 사람이 자주 끊긴다(S8 전까지).

### 결정할 것

1. 손님: 로그인 없이 노는 것을 서버 쪽 손님 캐릭터로 유지할지(추천), 공유 세계는 로그인한 사람만 들어오게 할지.
2. 기존 저장: 이 기기의 저장을 검사해서 가져올지, 서버 세계는 새로 시작할지, 가져오되 레벨이나 코인에 상한을 둘지.
3. 이야기 보스: 파티 인스턴스(최대 8명, 추천), 공유 세계 보스, 둘 다.
4. 처치 보상: 때린 사람 모두 전부 받기, 파티끼리 나누기, 처음 때린 사람만.
